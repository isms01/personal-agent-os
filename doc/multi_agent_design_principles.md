# マルチエージェント組織 設計原則ノート

**Date:** 2026-07-06
**Source:** 設計ディスカッション（Claude Code との対話）
**Status:** Draft — 運用しながら育てる

このノートは、エージェント組織（VISIONS.md の Agent Organization 構想）を
実装に落とすときの設計原則をまとめたもの。

---

## 1. 前提認識

- 企画 → 要件定義 → 設計 → コーディング → テスト をエージェントで繋ぐ
  開発サイクルは理想論ではなく現実に構築可能。業界全体がその方向に進んでいる。
- ただし成否を分けるのは「エージェントを並べること」ではなく、
  以下の設計課題への対処である。

## 2. 三大設計課題

### 2.1 エラーの複利効果

- 上流工程の小さな解釈ミスは、下流の全成果物を汚染する（複利的に増幅）。
- 対策の本丸は工程エージェントではなく **差し戻しループ（フィードバック設計）**。
  VISIONS.md 2.3 の Bird's Eye / Bug's Eye ループは飾りではなく生命線。

### 2.2 検証可能性の勾配

- 下流（コーディング・テスト）は出力を機械検証できる（テスト・lint の pass/fail）
  → 自律度を高くできる。今すぐ実用レベル。
- 上流（企画・要件定義）は「正解」の判定基準が外部に存在しない
  → 人間のチェックポイントを残す。
- **全工程を一律に自律化するのではなく、検証可能な下流ほど自律度を上げる勾配設計にする。**

### 2.3 オーガナイザーは動的であるべき

- 固定の直列工程はウォーターフォールの再現になる（後工程の発見を前工程に戻せない）。
- オーガナイザーの価値は工程の管理ではなく、
  「このタスクにどの工程が必要か」「どこで反復すべきか」の動的判断。
  （例: 小さい修正は実装→テストのみ、大きい機能は要件から）

## 3. 鉄の掟: 未定義は絶対に確認を取れ

- 上位成果物（神様データ）に書かれていないことは未定義であり、
  **未定義を勝手に解釈して作り込むことを許可してはいけない。**
- CLAUDE.md 行動規則 2 はこの掟の単体エージェント版。
  personal-agent-os は、マルチエージェント組織の統治ルールを
  単体エージェントで先行検証している。
- 「やらないこと」の明文化が、人間にも LLM にも暴走を止める上で重要。

### 3.1 難所: 「未定義であること」の検出自体が難しい

- LLM は空白を無意識に補完する（helpful に訓練されているため罪悪感がない）。
- 良い補完（文脈からの妥当な推論）と悪い補完（勝手な設計判断）の境界は
  機械的に定義できない。
- 対策: レビュー側エージェントに **トレーサビリティ検査** をさせる。
  成果物の各部分が仕様のどの文に根拠を持つかを対応付け、
  対応が取れない箇所 = 勝手な補完の疑い、として検出する。

### 3.2 神様データは「完全」ではなく「未定義の明示」で作る

- 自然言語の仕様書を完全無欠にするのは原理的に不可能。
- 現実的な神様データの姿は
  **決定事項と未決事項が明示的に分離されている文書**。
- 未定義が「書かれていない部分」に暗黙に存在するのが最も危険。
  未定義を一級市民として文書に書かせる。
- 下流エージェントは未決事項に触れた瞬間に機械的に停止・確認できる。

## 4. 決定の永続化: 確認のたびに仕様の完成度が単調増加する構造

- 確認質問への人間の回答は、会話で消さずに神様データの「決定事項」に追記する。
- 同じ質問は二度と来なくなる → 確認コストは時間とともに減少する。
- VISIONS.md「Decisions made (and the reasoning behind them)」の受け皿。

### 4.1 実装: ADR (Architecture Decision Records)

- `doc/decisions/` に 1 決定 = 1 ファイルで蓄積する。
- フォーマット: Status / Date / Context（なぜ必要になったか）/
  Decision（何を決めたか）/ Consequences（何が起こるか）。
- CLAUDE.md とは分離する:
  - CLAUDE.md = 「どう働くか」の規則。少数・安定・毎セッション常時読み込み。
  - 決定事項 = 「何を作ると決めたか」の記録。単調増加・随時参照。
  - 読み込まれ方（常時 vs オンデマンド）が違うものを混ぜると
    コンテキストを圧迫し、行動規則への注意も薄まる。
- CLAUDE.md 側には参照ルールを 1 行置くだけ:
  「実装前に doc/decisions/ の関連決定を確認し、矛盾する実装をしない。
  新たな決定が下されたら ADR として追記する」

### 4.2 運用上の注意: 確認の頻度設計

- 掟を厳格にしすぎると人間が割り込み地獄でボトルネック化する。
- 緩衝層が必要:
  - 質問のバッチ化
  - オーガナイザーが既存の決定事項から回答できる質問を先に捌く

## 5. コスト設計

- エージェント間通信はそれ自体が LLM 呼び出し。多段構成では
  1 タスクあたりの呼び出しが数十〜数百回になり得る。
- 差し戻しループは同一タスクで何往復も呼び出しを発生させる。
- 長期記憶の都度参照はコンテキストのトークン量も増やす。
- **どの判断に LLM が必要で、どの判断はルールベースで済むかの切り分けが
  実用化の分水嶺。** キャッシュ・要約による圧縮も検討する。

## 6. 進め方（Pragmatic First との整合）

1. まず検証可能な小さい閉ループから始める:
   **実装エージェント + テストエージェント + 差し戻しループ**
2. そこで得た知見（差し戻し判断の設計、確認頻度の調整）を上流に広げる。
3. 全工程の一斉構築はしない。
